# TF 根化补丁说明（base_footprint 当根）

> 这份文档只讲一件事：**为什么要把 `base_footprint` 提到 TF 树的最上面，怎么改的，出问题怎么查。**
> 代码在 `scripts/model_patches.py` + `scripts/prepare_setup.py`，别处不用看。
> 最后更新：2026-10-20（第 2 步）。

---

## 1. 一句话

A200 的 URDF 里，`base_footprint`（地面投影）被挂成了 `base_link`（车体）的**子节点**——方向反了。
把它翻过来当根，同时改 ekf 和差速控制器两处配置，让 `odom → base_footprint → base_link → …` 成为唯一链条。

## 2. 为什么非改不可

- **Nav2 / MoveIt 的惯例**是拿 `base_footprint` 当机器人基准帧（它在**地面上**，判断“车能不能过这个门”用的是它）。
- TF 必须是**树**：每个帧只能有一个父。`base_footprint` 从子变根，就必然改变 `base_link` 的父是谁。
- 我实测过：**多出一个父节点时 tf2 不报错**，只是“谁最后写谁生效”，你查到的位置取决于时序——这类错误只能靠断言发现，眼睛看不出来。

## 3. 改的三处（缺一不可）

| # | 文件（生成物） | 改什么 | 不改会怎样 |
|---|---|---|---|
| 1 | `robot.patched.urdf` ← 由 `robot.urdf.xacro` 展开后打补丁 | `base_footprint_joint` 的 parent/child 对调；偏移 `(0,0,-0.13228)` → `(0,0,+0.13228)` | 树根还是 `base_link`，等于什么都没做 |
| 2 | `platform/config/localization.yaml` | `base_link_frame: 'base_link'` → `'base_footprint'` | `base_link` 同时被 `odom` 和 `base_footprint` 当子节点（双父） |
| 3 | `platform/config/control.yaml` | `base_frame_id: 'base_link'` → `'base_footprint'` | 里程计话题的 `child_frame_id` 还写着 `base_link`，与 TF 不一致 |
| 4 | `robot.patched.urdf` 里的 `<sensor name="lidar2d_0">` | `update_rate: 50` → `bringup.yaml` 的 `lidar_update_rate`（默认 15） | 软渲染下 50 Hz 是 CPU 大头（实测 RTF 0.24 → 15 Hz 后 0.45） |

数学上很简单：只有平移、旋转为零，所以逆变换就是把三个数取负。不需要算矩阵。

## 4. 文件地图

```
q2q_harness/sim/robot_bringup/
├── launch/bringup.launch.py       启动入口；启动前调用 prepare_setup.py
├── config/robot.yaml              机器人本体真源（唯一手改的地方）
├── config/bringup.yaml            运行参数
└── scripts/
    ├── prepare_setup.py           编排：调 4 个生成器 → 打补丁 → 校验
    └── model_patches.py           三个补丁 + 校验函数（真正干活的地方）
```

生成物在 `~/.q2q/setup/a200_kinova/`（**可随时删除**，下次启动会重建）：

| 文件 | 是什么 | 谁写的 |
|---|---|---|
| `robot.yaml` | 从包里同步过来的本体配置 | `bringup.launch.py` |
| `robot.urdf.xacro` | **被替换成包装器**（只做 include） | `model_patches.py` |
| `robot.raw.urdf` | xacro 展开后的原始模型（中间产物，排障用） | `model_patches.py` |
| `robot.patched.urdf` | 打过补丁的最终模型 | `model_patches.py` |
| `platform/…`、`sensors/…`、`manipulators/…` | 生成器产出的 launch 与参数 | 生成器 |

## 5. 启动链

```
ros2 launch robot_bringup bringup.launch.py
│
├─ 1. 同步 config/robot.yaml → ~/.q2q/setup/a200_kinova/robot.yaml
├─ 2. prepare_setup.py（阻塞约 10 秒，任一步失败就中止整个 launch）
│     ├─ generate_description       → robot.urdf.xacro（原始 xacro）
│     ├─ generate_semantic_description → robot.srdf
│     ├─ generate_launch / generate_param → 各层 launch 与 yaml
│     ├─ 打三个补丁
│     └─ 校验（根/父/多父/link 数/两个 yaml 的值）
├─ 3. Gazebo + clock 桥
└─ 4. Clearpath robot_spawn（generate:=false，不会重新生成覆盖补丁）
```

> **关键 1**：`generate:=false` 必须一直传进 `robot_spawn`。如果让它自己生成，会把补丁后的文件覆盖回原始版本，而且**没有任何报错**。
>
> **关键 2**：展开 URDF 时必须原样带上 RSP 那 6 个参数（尤其 `is_sim:=true`）。漏了它，展开出来的是「真实机器人串口硬件」版本：`<plugin>clearpath_hardware_interfaces/A200Hardware</plugin>`，Gazebo 里没有 `ign_ros2_control` 插件 → 没有 `controller_manager` → **所有控制器 spawn 失败、没有里程计、没有 joint_states**，但机器人模型照样出现在画面里，很容易误判成"跑起来了"。这个坑已经踩过一次，现在由 `verify()` 里的两条断言兜住。
>
> **关键 3**：`use_manipulation_controllers` 必须是 `true`。它是 `false` 时，机械臂关节根本不会被写进 `<ros2_control>`，没有命令接口，两个臂控制器激活时会报 `Not acceptable command interfaces combination`（底盘控制器却正常，所以现象是"车能动、臂不动"）。`verify()` 也会检查模型里有没有 `command_interface name="position"`。

## 6. 出问题怎么查（按症状找）

| 症状 | 先跑这条 | 结论 |
|---|---|---|
| 控制器 `spawner` 报 `process has died [exit code 1]`、没有 `/platform/odom`、`joint_states` 为空 | `grep -c 'IgnitionROS2ControlPlugin' ~/.q2q/setup/a200_kinova/robot.patched.urdf` | 结果是 0 → 展开时参数漏了（见第 5 节「关键 2」） |
| 底盘能跑，但两个臂控制器 `inactive`，报 `Not acceptable command interfaces combination` | `grep -c 'command_interface name="position"' ~/.q2q/setup/a200_kinova/robot.patched.urdf` | 结果是 0 → `use_manipulation_controllers` 传成了 false（见「关键 3」） |
| 启动直接失败，看到 `[prepare] 失败` 或 `[patches] 校验失败` | 手动跑一次：`python3 <share>/robot_bringup/scripts/prepare_setup.py --setup ~/.q2q/setup/a200_kinova` | 生成器或补丁逻辑变了，看它打印的具体断言 |
| 说「找不到 base_footprint_joint」 | `grep -c base_footprint_joint ~/.q2q/setup/a200_kinova/robot.raw.urdf` | 生成器升级、关节改名了，改 `model_patches.py` 里的 `ROOT_JOINT` |
| RViz / Nav2 里车的位置乱跳 | `ros2 run tf2_tools view_frames --ros-args -r /tf:=/a200_0000/tf -r /tf_static:=/a200_0000/tf_static` | 看 `base_link` 是不是有两个父（会显示两条箭头） |
| `tf2_echo odom base_link` 查不到 | `ros2 topic hz /a200_0000/tf` | 没数据 → ekf 没起来；有数据但查不到 → 父链断了 |
| 里程计话题和 TF 对不上 | `ros2 topic echo /a200_0000/platform/odom --once \| head -6` | `child_frame_id` 应该是 `base_footprint` |
| Gazebo 里模型不见了/报无惯量 | 看启动日志里 `ign gazebo` 的 warn | 见第 8 节风险 |

手动重跑（不启动仿真）：

```bash
source /opt/ros/humble/setup.bash
SHARE=$(ros2 pkg prefix robot_bringup)/share/robot_bringup
python3 $SHARE/scripts/prepare_setup.py --setup ~/.q2q/setup/a200_kinova
```

只想打补丁、不重新生成（省 10 秒，排障常用）：

```bash
python3 $SHARE/scripts/prepare_setup.py --setup ~/.q2q/setup/a200_kinova --skip-generate
```

## 7. 怎么回滚

删掉生成物，把 `generate` 留着 true 重启动即可；或者临时绕开补丁：

```bash
# 临时回到「base_link 当根」的原始状态
rm -rf ~/.q2q/setup/a200_kinova
# 然后手动跑生成器（不加补丁）：
ros2 run clearpath_generator_common generate_description -s ~/.q2q/setup/a200_kinova
# ……此时 TF 根是 base_link，ekf 配置也是 base_link，两边一致，能跑
```

注意：**不能只回滚 URDF 不回滚 ekf/control**，否则又是双父。

## 8. 已知风险 / 边界

1. **Gazebo 对无惯量根 link 的处理**：`base_footprint` 没有质量。它变成 URDF 根之后，URDF→SDF 转换可能警告或合并固定关节。验收时要确认 Gazebo 里模型完整、TF 帧数没掉。真出问题就给 `base_footprint` 加一个极小惯量。
2. **生成器升级会静默改字段**：所有补丁都带断言（找不到目标就退出）。所以如果哪天升级了 clearpath，先跑 `--skip-generate` 之外的那条完整命令，看断言有没有红。
3. **补丁只认这一套生成器输出**（clearpath 1.3.13）。换机器人（不是 A200）或改 `robot.yaml` 的底盘型号时，`base_footprint_joint` 可能换名字，需要重新核对。
4. **相机不在这里**。相机是第 5 步的事，加相机只需要改 `config/robot.yaml`（加 `sensors.camera` 和挂载点），补丁脚本不用动。

## 9. 以后加东西时要不要动这里

| 你要做的事 | 要动补丁吗 |
|---|---|
| 换机械臂 / 加夹爪 / 调传感器频率 | 不用，改 `config/robot.yaml` |
| 加相机（RGB-D） | 不用，改 `config/robot.yaml` |
| 换底盘型号（不是 A200） | **要**，重新确认根关节的名字和偏移 |
| 升级 Clearpath 版本 | **要**，先跑一次看断言 |
| 想改 Nav2 的 `robot_base_frame` | 不用改这里，但必须设成 `base_footprint` 与本文一致 |
