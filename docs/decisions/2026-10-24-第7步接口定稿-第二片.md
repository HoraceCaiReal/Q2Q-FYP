## 0. 结构变化（先说清，因为要动第一片的文件）

第一片把「测量 + 发布」放在 `worldstate_node` 一个文件里（89 行）。这一片要加状态机与 action 客户端，
再塞进同一个文件会超行数上限，也会把「纯逻辑」和「ROS 胶水」搅在一起。所以拆成三个模块：

| 文件 | 职责 | 是否依赖 ROS |
|---|---|---|
| `q2q_orchestration/measure.py` | odom/joint_states → 四个条件（新鲜/停稳/收拢/观测值） | 否（纯计算） |
| `q2q_orchestration/machine.py` | 状态机：状态 + 事件 → 新状态 + 动作清单（对应教程的事件表） | 否（可离线测） |
| `q2q_orchestration/orchestration_node.py` | ROS 胶水：订阅、action 客户端、定时器、发布 | 是 |

**入口名从 `worldstate_node` 改为 `orchestration_node`**，主题与消息不变。
`worldstate_node.py` 删除（它不是被覆盖隐藏，是真的被这三个文件取代）。

## 3. 接口五问

### I6 命令入口

| 问题 | 定稿 |
|---|---|
| 解决什么 | 让上层（或测试）用**事件**驱动一次导航任务，并且能被取消 |
| 通信类型 | `topic` |
| 对象类型 | `q2q_interfaces/msg/TaskCommand` |
| 谁发谁收 | 上层/测试 → `orchestration_node`，话题 `/q2q/mid/task_command` |
| 频率/QoS | 事件驱动（不周期发布），RELIABLE、KEEP_LAST 10 |
| 失败与超时 | 非法目标（走廊外）或机械臂未收拢 → 拒绝，`blocked_by` 写明原因；**同一 `request_id` 重复到达只处理一次** |

> 为什么用 topic 不用 service：事件模型便于重放与并发观察；反馈走 `TaskState`（同一份状态即回执），
> 不再引入第二个「应答」接口。代价：拒绝原因是**异步**回执，调用方要读状态。

### I7 导航执行（action 客户端）

| 问题 | 定稿 |
|---|---|
| 解决什么 | 把「去工位」变成一个可取消、可查终态的导航动作 |
| 通信类型 | `action` |
| 对象类型 | `nav2_msgs/action/NavigateToPose`（goal: `PoseStamped pose` + `string behavior_tree` 留空用默认） |
| 谁发谁收 | `orchestration_node` → Nav2，动作名 `/a200_0000/navigate_to_pose` |
| 频率/QoS | 一次任务一个 goal；feedback 用于更新 `distance_remaining` |
| 失败与超时 | **goal 被拒绝** → `nav_status=REJECTED`、状态回 `IDLE`；**超过 `timeout_s`** → 只发一次 `cancel_goal_async()` 并进入 `CANCELING`；终态 `SUCCEEDED/CANCELED/ABORTED` 按 status 4/5/6 处理；**目标 id 不匹配的结果记为迟到事件**，不推进状态 |

### I8 状态回执（`TaskState` 扩展）

| 问题 | 定稿 |
|---|---|
| 通信类型 | `topic`（沿用第一片的 `/q2q/mid/task_state`） |
| 对象类型 | `q2q_interfaces/msg/TaskState`（新增 5 字段，见 §2） |
| 谁发谁收 | `orchestration_node` → `state_recorder` 等消费者 |
| 频率/QoS | 10 Hz（不变） |
| 失败与超时 | 与第一片一致；`late_events` 单调递增，重放时可核对 |

### I9 参数（新增）

| 参数 | 默认 | 校验 |
|---|---|---|
| `nav_action` | `/a200_0000/navigate_to_pose` | 非空 |
| `nav_timeout_s` | 90.0 | 0 < t ≤ 600 |
| `station_x` / `station_y` / `station_yaw` | 0.85 / 0.0 / 0.0 | 目标走廊内 |
| `corridor` | 0.20 1.20 -0.60 0.60 | xmin xmax ymin ymax，`corridor[0]<corridor[1]` 等 |

## 4. 状态机事件表（教程 13 章「先用事件表考验设计」）

| 当前 | 事件 | 守卫 | 下一状态 | 动作 | 备注 |
|---|---|---|---|---|---|
| IDLE | START | `arm_stowed` 且目标在走廊内 | NAV_TO_PICK | 发 goal 一次 | 否则留下 `blocked_by` |
| IDLE | START | 机械臂未收拢 | IDLE | 无 | `blocked_by=arm_not_stowed`（练习 13-A） |
| NAV_TO_PICK | NAV SUCCEEDED | `base_fresh` 且 `base_stopped` | WAIT_STILL | 无 | 停稳是**物理观测**，不是「导航说到了」 |
| NAV_TO_PICK | NAV SUCCEEDED | 还没停稳 | NAV_TO_PICK | 无 | `blocked_by=waiting_stop` |
| NAV_TO_PICK | NAV ABORTED / CANCELED(外部) | — | FAILED | 无 | 记录原因 |
| NAV_TO_PICK | CANCEL | — | CANCELING | 发 cancel 一次 | |
| NAV_TO_PICK | 超时 | `now-started > timeout_s` | CANCELING | 发 cancel 一次 | `nav_status=TIMEOUT` |
| WAIT_STILL | tick | 永远（PICK 未实现） | WAIT_STILL | 无 | `blocked_by=base_command_locked` |
| WAIT_STILL | CANCEL | — | IDLE | 无 | |
| CANCELING | NAV CANCELED | — | IDLE | 无 | 正常取消 |
| CANCELING | NAV SUCCEEDED | — | IDLE | **记迟到事件** | 取消前已成功：不推进，但要留痕 |
| CANCELING | NAV ABORTED | — | FAILED | 无 | |
| FAILED | START | 同上 | NAV_TO_PICK | 发 goal 一次 | 重试要换 `request_id` |
| 任意 | 结果 id 不匹配 | — | 不变 | `late_events += 1` | 不偷偷丢 |

## 5. 验收（这一片怎么算通过）

1. 冷启动后机械臂在零位 → `arm_stowed=true`；发 `START` → `IDLE → NAV_TO_PICK`，车真的开到工位。
2. 导航成功但车还在滑行时停在 `NAV_TO_PICK`（`blocked_by=waiting_stop`）；停稳 0.5 s 内进 `WAIT_STILL`。
3. 进 `WAIT_STILL` 后不再有任何转移（PICK 未实现），`blocked_by=base_command_locked`——**不许自己动臂**。
4. 另起一轮，导航中途发 `CANCEL`：状态进 `CANCELING`，Nav2 终态 `CANCELED`，1 s 内底盘物理速度归零，回 `IDLE`。
5. 重复发同一个 `request_id` 的 `START`：只发一次 goal（`nav_goal_id` 不变）。
6. 机械臂未收拢时发 `START`：状态不变，`blocked_by=arm_not_stowed`（用参数化单元测试覆盖，不必真动臂）。
7. 离线跑 `machine.py` 的事件表断言（不依赖 ROS），把上表逐行验证一遍。
8. 全程 `state_recorder` 正常记录，`late_events` 与 `nav_status` 可核对。

### 途中修掉的两个真 bug（都是「看起来对、数据不对」）

1. **`active_goal` 赋值时机错**：原来在**发 goal 时**读 `nav.pending`，而 `send_goal_async` 是异步的，
   那一刻拿到的是**上一个**目标的 id → 真终态被当成「迟到」丢弃，状态卡在 `CANCELING`。
   修法：把真实 id 在 goal-response 回调里回传给状态机（`NavClient(on_goal=...)`）。
2. **记录器字段漏了新增的 5 个**：`state_recorder.FIELDS` 还是第一片的元组，`nav_status` 等写不进 JSONL。
   修法：补字段，并让存档脚本对缺失字段报错而不是静默。

### 一个关于精度的发现（影响下一片）

Nav2 默认 `xy_goal_tolerance` 很宽：目标 `0.85` 实际停在 **`0.717`**（差 13 cm），
而第 6 步的抓取走廊要求 `0.86–0.90`。也就是说**导航到位 ≠ 到达抓取位**。
现有管线里 `station_approach.py` 就是干这个的（真值辅助短距对接）。
所以 **slice 3 应该是**：`WAIT_STILL` 之后串一段「真值短距对接」→ 再用物理停稳 + 控制权锁定去开 `PICK` 的门。
不要指望把 Nav2 的容差调小来解决——那是拿导航参数去兜抓取的精度。
