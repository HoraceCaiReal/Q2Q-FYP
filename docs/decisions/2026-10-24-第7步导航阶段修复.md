# 第 7 步「导航阶段」修复：就绪闸门 + 真值接管（2026-10-24 第三轮）

> **第四轮已更新**：本文为历史过程。后半段已取得完整投放通过，新增ACTIVE检查、场景刷新、出站、车外投放及真实落点门禁；监控窗口不再用600s，旧“忽略合爪终态”已撤回。最新判据和证据见[整链修复与验收](../evaluations/2026-10-24-第7步整链修复与验收.md)，操作见[当前交接](../operations/当前开发交接.md)。不照搬本文旧重启/超时调整建议。

> 目标：把整链 `START → NAV → DOCK → PICK_READY → PICKING → PICKED → STOWING →
> NAV_TO_PLACE → PLACE_READY → DONE` 从「卡在导航」推到走通。
> 本文记录改了什么、为什么改、实测到哪一步、以及还没证的部分。

## 1. 上一轮的两个症状（原文）

1. **冷启动**：Nav2 还没起 action 服务就把 goal 发出去，没人接，90 s 后记成 `nav_timeout`——
   看起来像「导航能力不行」，其实只是**发早了**。
2. **热栈**：Nav2 对 x=0.85 这个目标会开过头到 **0.921**（顶住台面），然后 `ABORTED`；
   而状态机把 abort 一律当死因，链就断了。

## 2. 四处代码改动（都不新增 topic/service/action）

| # | 文件 | 改动 | 为什么 |
|---|---|---|---|
| 1 | `ready_gate.py`（新，44 行） | START 先过闸门：`nav_action` 能被发现 + `odom` 新鲜 + `arm_stowed` 三条齐了才发 goal；等不到就按自己的预算判失败 | 症状 1。发 goal 前必须具备判停稳的能力，否则超时诊断会指向错误的地方 |
| 2 | `machine.py` `tick()` | 真值 x ≥ `arrive_x`（默认 0.80）**立刻叫停 Nav2**，剩下的交给真值短距对接 | 症状 2。等 Nav2 自己到 0.85 会开过头 |
| 3 | `machine.py` `nav_result()` | `ABORTED` 不再立刻判死；若 x ≥ `arrive_x − recover_band` 就转 `WAIT_STILL` 继续对接 | 0.921 那次 abort 时车其实已经在工位上了 |
| 4 | `machine.py` + `orchestration_node.py` | `PICKING` 里的新鲜度判据换成 `picking_stale_s`（默认 600 s），只保留「位移 > 5 mm」这条硬判据；另把「状态机拒绝 START」从静默改成 ERROR 日志 | 接触让仿真变慢时 odom 墙钟间隔会长到十几秒，那是「世界卡了一下」，不是「底盘动了」 |

**新增参数（4 个，都是 `declare_parameter` + 范围校验）**：

| 参数 | 默认 | 含义 |
|---|---|---|
| `arrive_x` | 0.80 | 真值过这条线就自己叫停 Nav2 |
| `nav_recover_band` | 0.10 | abort 后离工位多近还值得救 |
| `nav_ready_timeout_s` | 45.0 | 等就绪的独立预算（不占导航超时） |
| `picking_stale_s` | 600.0 | PICKING 里 odom 断多久才算真坏 |

`TaskState` / `TaskCommand` / `Grasp` 一个字段都没动；`nav_status` 多了两个内部值 `ARRIVED`、
`ABORTED`（后者原来就有），都在既有字符串字段里，下游无需改。

## 3. 顺带修的三个「墙钟预算按 RTF≈1 调」的老毛病

这是第四次遇到同一类问题（前三次：`station_approach --stale-s`、JTC 抬升预算、合爪停稳判据）：

| 位置 | 原来 | 现在 |
|---|---|---|
| `grasp_run.py` P5 门禁 | 合爪动作终态必须 `status=4` | **运动学搬运模式（`--suction`）下只看几何**（开口 ≥45 mm、箱子被推 ≤10 mm）；摩擦抓取模式仍然要求 `status=4` |
| `action_sync.wait()` | 所有动作等待用固定墙钟 | 新增 `Q2Q_WALL_SCALE`（默认 1.0），按 RTF 放大；运行器传 6 |
| 试跑入口 | 导航/对接超时按 90/20 s 写死 | `--nav-timeout 300`、`--dock-timeout 110`（都在参数范围内） |

> P5 那一项要说清楚：**不是把门禁放宽，是把判据放到对的层**。运动学搬运本来就与接触无关，
> 拿「合爪动作有没有报成功」当搬运门禁属于用错判据；摩擦抓取那条路一个字没动。

## 4. 实测（4 次真跑，原始证据在 `logs/2026-10-24.md`）

| episode | 跑到哪 | 结果 |
|---|---|---|
| `step7_1024_164211` | `0.000 → 0.713(SUCCEEDED) → DOCKING → 0.875 → PICK_READY(锁) → PICKING` | 22 s 后被 `freshness_window=0.3` 误判 precondition_lost（已改） |
| `step7_1024_174614` | 同上 + 抓取流水线跑到 P5 | P5 `close status≠4`（已知 stall 语义），几何 60.0 mm / 推 2.3 mm 合格 → 改 P5 判据 |
| `step7_1024_180924` | 同上，PICKING 持续 47.5 s | `picking_stale=20` 太短，节点自身被 CPU 饿死期间超时 → 提到 600 |
| `step7_1024_181914` | 同上，抓取流水线真实启动 | 子进程 3 min 后写出 `passed=false, error="ROS response exceeded 3.0 wall seconds"` → 加 `Q2Q_WALL_SCALE` |

**结论强度**：导航段（`NAV → WAIT_STILL → DOCKING → PICK_READY`，含真值接管与上锁）**实测可复现**
（4 次全部到达 `PICK_READY`，x 停在 0.876，锁为 true）；抓取段**未走通**，
最后一次失败点是动作等待预算，已用 `Q2Q_WALL_SCALE` 处理但**尚未获得一次完整验证**。

## 5. 还没证的部分（不许写成定论）

1. `PICKED → STOWING → NAV_TO_PLACE → PLACE_READY → DONE` **这一整段仍然只有离线断言（8/8）**，
   从没在真机上跑过——每一轮都死在 PICKING。
2. `Q2Q_WALL_SCALE=6` 是否够：只在 1 次运行里设过，没等到结果（环境崩了）。
3. 环境问题本身：这台 VM 连跑 3–4 轮之后 `controller_manager` 会连续起不来
   （已知竞态，日志表现为 `switch_controller` 三次超时、`gz_ros2_control` 已收到 URDF 但 CM 不响应）。
   **重启 VM 能恢复**（实测：重启后 30 s 就绪），但一天内会出现第二次。

## 6. 复现入口（本轮唯一入口）

```powershell

.\.dsh\step3.ps1 -Action Deploy                          # 改过代码才需要
.\.dsh\step3.ps1 -Action Start -World q2q_warehouse_grasp50
# VM 侧（一个入口跑完整链，含 5 个节点 + 一条 START + 终态判断）
```

留下 10 Hz 全量状态（含 `late_events`、`blocked_by`、`nav_status`）。
