## 0. 范围与已知边界（先说清）

- 这一片**只做 PICK**：`PICK_READY → PICKING → PICKED`。`STOW`/`NAV_TO_PLACE`/`PLACE` 不做。
- **夹持不持久是已知边界**：第 6 步实测 2 过 5 败、抬起来后静置会掉（
  [夹持力与 P7 复核](../evaluations/2026-10-24-夹持力与P7复核.md)）。
  所以这一片的成功判据是「抓取流水线按 P1–P6 跑完并由它自己给结论」，
  **不把「夹住」当作流程通过的必要条件**——流程通过 = 请求发出、执行、拿到结构化结果、状态正确流转。

## 1. 新动作：`q2q_interfaces/action/Grasp`

```text
# goal
string target_id        # 目标 id（当前固定 pick_bin，留给以后的跟踪器）
float64 timeout_s       # 整条流水线的时间预算；<=0 用参数默认
---
# result
bool success            # 流水线自己的判定（P1–P6 全过才 true）
string reason           # 失败时给阶段名，如 P5_contact_failed
float64 rise_mm         # 抬升累计（成功时才有意义）
---
# feedback
string phase            # 当前阶段名（open/pregrasp/insert/close/lift…）
```

## 2. 接口五问

### I14 抓取执行（action 服务端）

| 问题 | 定稿 |
|---|---|
| 解决什么 | 把「执行一次抓取流水线」变成可取消、有结构化结果的动作 |
| 通信类型 | `action` |
| 对象类型 | `q2q_interfaces/action/Grasp` |
| 谁发谁收 | `orchestration_node` → `grasp_executor`（下层执行器），动作名 `/q2q/low/grasp` |
| 频率/QoS | 一次任务一个 goal；feedback 转发流水线的 PHASE 行 |
| 失败与超时 | 超过 `timeout_s` → 杀掉子进程并返回 `success=false, reason=timeout`；`cancel` → 同样杀子进程、返回 `reason=canceled`；子进程非零退出 → 把它的 JSON 里的 `error` 原样放进 `reason` |

> **实现选择（临时但有边界）**：`grasp_executor` 现在是**适配器**，内部调用已经验证过的
> `robot_bringup/scripts/grasp_run.py`（子进程），把它自己的 P1–P6 判定翻译成 action 结果。
> 这样做的原因是第 6 步的流水线已经带门禁与 JSON 证据，先让第 7 步跑通整链；
> **代价**：多一层进程、feedback 只能按行解析。后续把逻辑内联进执行器时，接口不变。

### I15 编排侧状态与动作

| 项 | 定稿 |
|---|---|
| 新状态 | `PICKING`（已发出 grasp goal，等结果）、`PICKED`（流水线返回 success） |
| 转移 | `PICK_READY --(四条前置成立)--> PICKING`（发一次 goal）；`PICKING --success--> PICKED`；`PICKING --fail--> FAILED`（解锁）；任意 --CANCEL--> 取消 grasp goal，解锁 → `IDLE` |
| 解锁时机 | `PICKED` 保持锁定（臂还夹着东西，底盘不许动）；`FAILED`/`IDLE` 必解锁 |
| 新增动作 | `('grasp',)`、`('cancel_grasp',)` |

## 3. 验收

1. `START → NAV → DOCKING → PICK_READY`（第三片已验），随后**自动**进入 `PICKING`（不需要第二条命令）。
2. `PICKING` 期间 `base_command_locked=true`、`blocked_by=picking`；流水线的 phase 能从 feedback/日志看到。
3. 流水线结束：
   - 成功 → `PICKED`，`blocked_by=picked_hold`（臂持物，底盘仍锁）；
   - 失败 → `FAILED`，`reason` 里带流水线给的阶段名，并**解锁**。
4. `CANCEL` 在 `PICKING` 中：杀掉流水线子进程、解锁、`IDLE`；**不允许残留 subprocess**。
5. 记录：JSONL 里有 `PICK_READY → PICKING → PICKED/FAILED` 的转移与 `base_command_locked` 的翻转。
6. **诚实标注**：即使这次流水线 `success=false`（夹持问题），只要流程与记录正确，本片仍算通过。

### 途中修的一个 bug（自己写出来的）

`PICKING` 的前置检查原先沿用 PICK_READY 的四条（含 `arm_stowed`）。但臂一开始动，
`arm_stowed` 必然变 false → 会把自己的抓取判成「前置丢失」并取消。已改成
**PICKING 只盯「底盘新鲜 + 停稳」**，底盘一动就取消臂（离线断言已验证：
臂动不中断、底盘动则 `cancel_grasp + unlock`）。
