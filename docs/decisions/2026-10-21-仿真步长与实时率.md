# 裁决：仿真步长 max_step_size 0.003 → 0.02（附实时率实测）

- 日期：2026-10-21
- 触发：建图/导航第一次真正「要机器跟得上」。RTF 只有 0.07 时，扫一张图要半小时，
  而且 controller spawner 会因服务响应超时而连环失败。
- 结论：`q2q_warehouse.sdf`（以及后续同规格的世界）**物理步长用 0.02 s（50 Hz）**。

## 1. 为什么必须动它（两个真实症状）

| 症状 | 表现 | 与 RTF 的关系 |
|---|---|---|
| 扫图不可行 | `/a200_0000/map` 5 s 才更新一次，激光等效 1 Hz | 车走 40 m 要 20+ 分钟墙钟时间 |
| 控制器起不来 | `A controller named 'joint_state_broadcaster' was already loaded`，spawner FATAL 退出 | 见第 4 节链路 |

## 2. 怎么量的（可复现）

量的是**仿真时间推进速度**，不是日志里那句 `real_time_factor` 的自报值：

```bash
# 仿真侧权威数据：iterations / sim_time / real_time / real_time_factor
ign topic -e -t /world/q2q_warehouse/stats -n 1

# 交叉验证：10 s 墙钟内 /clock 往前走了多少
#   throughput = Δsim_time / Δwall_time
```

两种量法结论一致（误差 < 10%）。

## 3. 实测：步长和吞吐成正比

同一世界、同一机器人、只改 `<max_step_size>`，取 10 s 窗口：

| max_step_size | 等效物理频率 | Δsim / Δwall | 迭代次数/秒 | 单次迭代开销 |
|---|---|---|---|---|
| 0.003（原值） | 333 Hz | **0.07** | ~18 | 55 ms |
| 0.005 | 200 Hz | 0.20 | 12 | 83 ms |
| 0.01 | 100 Hz | 0.30 | 12 | 83 ms |
| 0.02 | 50 Hz | **0.40** | 12 | 83 ms |
| 0.05 | 20 Hz | 0.60 | 12 | 83 ms |

**关键规律：迭代率几乎恒定为 ~12 次/秒，与步长无关。**
也就是说每跑一步都要交一笔约 83 ms 的固定开销（不是物理求解贵，物理量随步长变化却几乎不影响迭代率）。
所以「每秒推进多少仿真时间 ≈ 12 × 步长」，吞吐和步长成正比。

对照实验（把机器人拿掉，只跑空世界）：135 次/秒、单步 7.4 ms。
→ **这 83 ms 是机器人带进来的，不是世界带进来的**；世界里加 12 个货架/料箱对它没有可测影响
（`q2q_empty` 0.074 vs `q2q_warehouse` 0.070，在噪声内）。

再看两个"以为是它、其实不是它"的对照：

| 对照 | 结果 | 结论 |
|---|---|---|
| 激光 `update_rate` 15 → 2 Hz | 0.074 → 0.090 | 渲染不是主要开销 |
| 机器人 + 空世界 vs 机器人 + 仓库世界 | 0.074 vs 0.070 | 障碍物数量无关 |

（`gz_ros2_control` 的 `PreUpdate` 每个仿真步都要跑一遍 `controller_manager` 的 read/update/write，
是这 83 ms 的头号嫌疑；没有 ROS 侧源码可改，这一轮只做「按步长摊薄」的工程处理，
不做插件级优化——那是第 8 步的事。）

## 4. 连带解释：控制器 spawner 为什么间歇性 FATAL

2026-10-21 上午一直卡的报错，根因不是"控制器被别处加载了两遍"，而是**服务响应在 CPU 饥饿下超时**：

```
[ign gazebo-1] [WARN] [a200_0000.controller_manager.rclcpp]:
    failed to send response to /a200_0000/controller_manager/load_controller (timeout)
    client will not receive response
[ign gazebo-1] [INFO] [a200_0000.controller_manager]: Loading controller 'arm_0_joint_trajectory_controller'
[ign gazebo-1] [ERROR] [a200_0000.controller_manager]:
    A controller named 'arm_0_joint_trajectory_controller' was already loaded inside the controller manager
```

链路是：

1. spawner 调 `load_controller`；
2. controller_manager（跑在 Gazebo 进程里）**已经把控制器装好了**；
3. 但它的响应在 DDS 上超时（`rmw_response.cpp:154`），spawner 收不到；
4. spawner 重试 `load_controller`；
5. 第二次到达时控制器已存在 → controller_manager 回"already loaded"；
6. spawner 把这个回应当成致命错误，FATAL 退出；
7. 只要有一个控制器没被激活，`map` 帧不存在，slam_toolbox / Nav2 全线起不来。

所以「加内存、8 核 → 16 核」都没用：瓶颈是单进程内的串行开销与响应超时，
不是总 CPU。步长改大之后每个仿真秒要跑的步数减少，CPU 空出余量，这条超时链也就不容易触发。

## 5. 代价与边界

- 50 Hz 对轮式底盘够用：差速控制器上限 1.0 m/s，建图巡游按 0.45 m/s 走，每步位移 9 mm；
  差速控制器 `publish_rate: 50`，里程计不需要比控制更细。
- 不要为了更快再调到 0.05：20 Hz 物理对轮地接触的解算太粗，第 5/6 步做抓取/接触判断时会失真。
- `real_time_factor` 卡在 0.40 是**这台 VM 的天花板**，不是标定错误；验收命令一律用
  「等状态出现」而不是「等固定时长」（脚本里都是 `wait_for`）。

## 6. 复现命令

```bash
ign topic -e -t /world/q2q_warehouse/stats -n 1     # 权威 RTF
ros2 topic hz /clock                                # 交叉验证
```
