> **历史增量设计。** 后续已加入抓取、规划收臂、UNDOCKING及投放；当前停止确认和锁策略仍有待审计分支。以[当前交接](../operations/当前开发交接.md)和[交接待办](../../archive/2026-10-24-第7步交接/README.md)为准，不能把本页局部验证当作全异常验收。

> 依据教程 13 章的不变量 `arm_execute ⇒ base_fresh AND base_stopped_for_window AND base_command_locked`
> 与 [第二片定稿](2026-10-24-第7步接口定稿-第二片.md)。第二片证明「导航到位 ≠ 到达抓取位」
> （目标 0.85 停在 0.717，而抓取走廊要 0.86–0.90），这一片补最后 13 cm，并且第一次真的**锁住底盘**。

## 0. 新增两个状态

```text
WAIT_STILL --(不在走廊)--→ DOCKING --(进走廊 ∧ 物理停稳)--→ PICK_READY --(CANCEL)--→ IDLE
                              └--(超时/越界)--→ FAILED（并发零速、不锁）
```

- `DOCKING`：用**真值**闭环把车挪进抓取走廊；只用 `cmd_vel`，速度有上限，退出必定发零速。
- `PICK_READY`：四条前置条件同时成立（新鲜、停稳、**已锁定**、臂收拢）。这一片不接机械臂动作，
  所以进入后 `blocked_by=pick_executor_not_implemented` 并保持——**这是刻意的**：
  先证明「门能开、开着的时候底盘真的被锁死」，再谈让臂动。

## 1. 接口五问

### I10 真值短距对接（本节点自己开底盘）

| 问题 | 定稿 |
|---|---|
| 解决什么 | 补上 Nav2 停点（0.717）到抓取走廊（0.86–0.90）的最后一段 |
| 通信类型 | `topic` |
| 对象类型 | `geometry_msgs/msg/Twist` |
| 谁发谁收 | `orchestration_node` → twist_mux（`external` 输入）：`/a200_0000/cmd_vel` |
| 频率/QoS | 20 Hz（`dock_rate`），RELIABLE；只在 `DOCKING` 状态发布 |
| 失败与超时 | 速度上限 `dock_speed`（默认 0.08 m/s）；`dock_timeout_s`（默认 20 s）到点 → `FAILED`；**离开 `DOCKING` 必发一帧零速**；越界（x 超过走廊上限 +2 cm）立即零速并 `FAILED` |

### I11 控制权锁定

| 问题 | 定稿 |
|---|---|
| 解决什么 | 让「抓取期间底盘不得被任何来源推动」变成**真的限制**，而不是口头约定 |
| 通信类型 | `topic` |
| 对象类型 | `std_msgs/msg/Bool` |
| 谁发谁收 | `orchestration_node` → twist_mux 的 `e_stop` 锁（优先级 255、`timeout=0`）：`/a200_0000/platform/emergency_stop` |
| 频率/QoS | 事件驱动：进入 `PICK_READY` 发一次 `true`，离开发一次 `false` |
| 失败与超时 | **这个锁不会自己过期**（`timeout=0`）：节点退出/异常时必须在 `finally` 里发 `false`，否则底盘一直锁死；日志必须写明当时是否持有锁 |

> 为什么用 e-stop 锁而不是「一直发零速」：`cmd_vel` 与 Nav2 是**同一个 mux 输入（优先级 1）**，
> 谁最后发谁生效——那不叫锁定，叫抢方向盘。e-stop 锁是优先级 255 的**真闸门**。

### I12 状态字段

不新增消息字段。`TaskState.base_command_locked` 从「恒 false 的占位」变成**真实报告**
（本节点是否持有锁）；`blocked_by` 说明当前卡在哪一条。

### I13 新参数

| 参数 | 默认 | 校验 |
|---|---|---|
| `dock_window` | `[0.86, 0.90, 0.02, 0.04]` | `xmin<xmax`、后两项 >0（x 走廊、\|y\| 上限、\|yaw\| 上限） |
| `dock_speed` | 0.08 m/s | 0 < v ≤ 0.20 |
| `dock_timeout_s` | 20.0 | 0 < t ≤ 120 |
| `dock_rate` | 20.0 Hz | 0 < r ≤ 100 |
| `lock_topic` | `/a200_0000/platform/emergency_stop` | 非空 |

## 2. 事件表（第三片增量）

| 当前 | 事件 | 守卫 | 下一状态 | 动作 |
|---|---|---|---|---|
| WAIT_STILL | tick | 在走廊内 ∧ 停稳 | PICK_READY | `lock`（发一次 true） |
| WAIT_STILL | tick | 不在走廊 | DOCKING | 无（节点开始按真值发速度） |
| DOCKING | tick | 在走廊内 ∧ 停稳 | PICK_READY | `stop_base` + `lock` |
| DOCKING | tick | 超时 | FAILED | `stop_base`（`reason=dock_timeout`） |
| DOCKING | tick | x 超上限 +2 cm | FAILED | `stop_base`（`reason=dock_overshoot`） |
| DOCKING | CANCEL | — | IDLE | `stop_base` |
| PICK_READY | CANCEL | — | IDLE | `unlock` |
| PICK_READY | tick | 四条前置不成立（如 odom 变 stale） | FAILED | `unlock`（`reason=precondition_lost`） |
| PICK_READY | tick | 四条成立 | PICK_READY | 无；`blocked_by=pick_executor_not_implemented` |
| 任意 | 节点退出 | 持有锁 | — | `unlock`（`finally` 里兜底） |

## 3. 验收

1. `START → NAV_TO_PICK`，Nav2 停在 ~0.72；因不在走廊自动进 `DOCKING`。
2. `DOCKING` 用真值把车推进 `[0.86,0.90]`；进走廊且停稳后 `PICK_READY`，`base_command_locked=true`。
3. **锁的真实性**：在 `PICK_READY` 里对外发 `cmd_vel`（0.1 m/s，2 s），**底盘不得移动**（真值位移 < 5 mm）。
4. `CANCEL` → 解锁 → `IDLE`；再发 `cmd_vel`，底盘**能**动（证明锁真的被解开，不是车坏了）。
5. 全程零速收尾：离开 `DOCKING` 后 1 s 内真值速度归零。
6. 记录：JSONL 里能看到 `WAIT_STILL → DOCKING → PICK_READY → IDLE` 与 `base_command_locked` 的翻转。

### 边界（必须保留）

1. **这一片没有让机械臂动**。进 `PICK_READY` 后 `blocked_by=pick_executor_not_implemented` 是刻意的：
   先把「门能开、开着时底盘真被锁死」证明清楚，下一片才接臂。
2. 锁用的是 twist_mux 的 `e_stop` 锁（优先级 255、**`timeout=0` 不会自己过期**）。
   节点在 `finally` 里兜底发 `false`，但**如果进程被 `kill -9`，锁会留在真值上**——
   下次接手先确认 `base_command_locked` 的日志，或手动发一次 `false`。
3. 对接只用 x 方向速度；`|y|≤0.02`、`|yaw|≤0.04` 是**判据**不是控制量：导航把车停歪了会走
   `dock_timeout` → `FAILED`，不会自己纠偏。要纠偏得另开接口。
