# 裁决：激光改用几何射线（virtual_lidar.py）

- 日期：2026-10-21
- 触发：地图一个障碍格都没有（自由 15.6% / 未知 84.4% / **障碍 0%**）。
- 结论：这台 VM 的 GPU 渲染拿不到深度，**保留原 CLEARPATH 模型不动**，另起
  `scripts/virtual_lidar.py`：读世界 SDF 的长方体做 2D 射线求交，按 15 Hz 发标准 `LaserScan`。
  原渲染激光的桥接话题改名 `scan_raw`，`scan` 让给虚拟激光。

## 1. 现象：激光一直「有话题、没数据」

从第 1 步起，激光验收就只看到「24.999 / inf」，当时被当成正常。今天量清楚了：

```python
{'n': 720, 'finite': 8, 'rmin': 24.999, 'rmax': 24.999, 'range_max': 25.0,
 'frame': 'lidar2d_0_laser'}
```

720 束里只有 **8 束**有值，而且**全等于 24.999 ≈ range_max**——意思是「什么都没打到」。
仓库里最近的料箱 0.4 m、货架 2 m、墙 6 m，不可能一束都打不着。

结论：slam 只能把射线终点画成自由空间（`max_laser_range` 以内），永远画不出障碍格。

## 2. 排查过的六条路（都失败）

| 尝试 | 结果 |
|---|---|
| `--headless-rendering`（ogre2 走 EGL） | 仍是 8 束、全 24.999 |
| `DISPLAY=:0` 起仿真（Xwayland） | 同上 |
| 传感器类型 `gpu_lidar` → `lidar`（CPU 激光） | Fortress 没有 CPU 激光实现，**一帧都不发** |
| 束数 720 → 180 | 变成 **0 束**有值（更裸露） |
| `EGL_PLATFORM=surfaceless` + `LIBGL_ALWAYS_SOFTWARE=1` | 0 束 |
| `MESA_LOADER_DRIVER_OVERRIDE=swrast`（llvmpipe） | 把 controller_manager 拖死，`load_controller` 连超 3 次 |

`glxinfo -B` 的根因证据：

```
OpenGL vendor string:   VMware, Inc.
OpenGL renderer string: SVGA3D; build: RELEASE;  LLVM;
Accelerated:            no                     ← 关键
Video memory:           1MB
OpenGL core profile:    4.1  (Core Profile) Mesa 23.2.1
```

即：Guest Additions 7.2.18 已装、`accelerate3d=on`、显存 128 MB（VMSVGA 上限就是 128），
但客户机 GL 仍是「SVGA3D 的软件回退」，只到 GL 4.1。ogre2 在这条路上拿不到深度缓冲。
宿主侧 `VBoxManage modifyvm --vram 256` 也改不进去（运行中锁 + VMSVGA 上限）。

## 3. 改法

| 文件 | 改动 |
|---|---|
| `scripts/virtual_lidar.py` | **新增**：解析 SDF 的轴对齐长方体 → 每帧按激光位姿做 720 条 2D 射线 → 发 `LaserScan` |
| `scripts/model_patches.py` | 新增 `patch_sensor_topic()`：把 `sensors/config/lidar2d_0.yaml` 的 `ros_topic_name` 改成 `lidar2d_0/scan_raw`（原渲染桥接还在，挪开避免两个发布者） |
| `launch/bringup.launch.py` | T+12 s 起虚拟激光，并加 `-r /tf:=/a200_0000/tf`（tf2_ros 默认订绝对名 `/tf`） |

实测输出（机器人停在原点）：

```python
{'n': 720, 'finite': 544, 'rmin': 0.4, 'rmax': 8.05, 'frame': 'lidar2d_0_laser'}
```

544 束有值、最近 0.40 m（料箱）、最远 8.05 m（墙角），和世界布局对得上。

## 4. 边界（论文里必须写清楚）

1. **只支持轴对齐长方体**：我们的世界是 3 面墙 + 4 组货架 + 4 个料箱，全是 box；
   换网格模型/斜面就失效（`load_boxes` 会跳过带旋转的模型）。
2. **无噪声、无反射率**：测距是理想值，比真实激光「干净」。所以代价地图/AMCL 的表现会比真实传感器乐观。
3. **不含自遮挡**：射线从激光中心发出，不模拟车体自身遮挡。
4. 上层**一行没改**：Nav2、slam_toolbox、AMCL 拿到的就是标准 `sensor_msgs/LaserScan`，
   所以「导航链路」这一层的验收是真实的；只有「传感器从哪来」这一环是几何替代。

## 5. 什么时候能换回真激光

宿主把 3D 真正开起来（或换一台能跑 ogre2 的机器）之后：

1. `model_patches.py` 里删掉 `patch_sensor_topic(setup)` 这一行（桥接恢复发 `scan`）；
2. `bringup.launch.py` 里删掉虚拟激光那个 `TimerAction`；
3. 重扫一次图。

上层参数、launch 结构、Nav2 配置都不用动。

## 6. 回归原生激光检查单（2026-10-22 起执行）

> 背景：用户 2026-10-21 夜里把虚拟机**显存改成 256 MB**。先确认这一改动真的生效，
> 再决定要不要摘掉这套替代方案。

**第 0 步：先验 GL，别急着改代码**

```bash
DISPLAY=:0 glxinfo -B | head -12
```

| 结果 | 判断 | 动作 |
|---|---|---|
| `Accelerated: yes`（Video memory 256MB） | 3D 真开了 | 继续第 1 步 |
| `Accelerated: no` | 宿主 3D 后端没起来，显存不是瓶颈 | **停**，保留虚拟激光，把这条写进环境限制 |

**第 1~4 步：逐条恢复并验数据**

1. `model_patches.py`：删掉 `apply_all()` 里的 `patch_sensor_topic(setup)`；
2. `model_patches.py`：把 `patch_lidar_rate()` 里的 `always_on.text = 'false'` 改回 `'true'`
   （并同步改 `verify()` 里的断言，否则启动会被自己的校验拦住）；
3. `bringup.launch.py`：删掉 `VIRTUAL_LIDAR_DELAY` 那个 `TimerAction`（虚拟激光），
   同时把 `patch_sensor_topic` 造成的 `scan_raw` 话题还原；
4. 起仿真，读一帧 LaserScan，**≥500 束有值、最近 0.4~1 m** 才算原生激光可用；不达标就回滚这四步。

**验收记录**：改回原生后重扫一次图，与 `q2q_warehouse.pgm`（几何射线版）对比
障碍形状是否一致——两者应当高度重合，差异只在噪声。
