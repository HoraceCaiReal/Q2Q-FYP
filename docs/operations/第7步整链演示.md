# 第 7 步整链演示（Full Process Demo）

> 一条命令跑完整的「走到工位 → 对接 → 抓取 → 收臂 → 出站 → 运到投放点 → 投放 → DONE」，
> 并落一套可复核的证据。**这是运动学支撑近似**，不是摩擦夹持、不是物理吸附。
> 图：[第7步整链节点流图](../../讲解/课程/figures/第7步整链节点流图.html)（PNG 同名）。
> 验收细节：[第7步整链修复与验收](../evaluations/2026-10-24-第7步整链修复与验收.md)。

## 1. 演示的是什么

一次任务的 12 个状态，全部由 `orchestration_node` 一个状态机推进，**只有一条 START 命令**：

```text
IDLE → NAV_TO_PICK → WAIT_STILL → DOCKING → PICK_READY → PICKING
     → PICKED → STOWING → UNDOCKING → NAV_TO_PLACE → PLACE_READY → DONE
```

每一段都有可复核的证据，不靠"看起来动了"：

| 段 | 判据（物理真值） | 证据来源 |
|---|---|---|
| 导航 + 对接 | 停在 x=0.876（窗口 0.86–0.90），横向/偏航在窗内 | `/a200_0000/ground_truth/odom` |
| 抓取 | 流水线自己的 P1–P6 门禁 + 动作终态 | `grasp_action_*.json` |
| 收臂 | JTC 终态 + 关节到位 | `orch.log` / `rec.log` |
| 出站 | 后退到 `x ≤ 0.64` 且停稳后才允许 Nav2 接管 | 状态转移 `UNDOCKING → NAV_TO_PLACE` |
| 投放 | 独立落地门禁：相对车前方 (.40, 0) m 的 xy 误差 < 80 mm、中心 z 15–40 mm、连续 3 帧位移 < 5 mm | `ign topic -t /world/.../pose/info` |
| 全程 | `late_events=0`、锁最终释放、JSONL 10 Hz 不断 | `~/.q2q/records/<episode>/task_state.jsonl` |

## 2. 怎么跑

### 2.0 一键（答辩用这个）

```powershell
Set-Location 'E:\毕设'
& .\.dsh\demo.ps1                 # 起栈 + 挂 Gazebo 窗口 + RViz + 跑整链 + 自动截关键帧
& .\.dsh\step3.ps1 -Action Stop    # 收尾
```

`demo.ps1` 做的事：停旧栈并清残留 → headless 起栈（50 mm + 运动学支撑）→ 轮询到
4 控制器 active + nav action 可用 → 挂 Gazebo GUI 客户端（ogre 引擎）与 RViz →
发一条 START 跑完整链 → **每当状态变化就在主机侧截一张图**，落到
`docs/evaluations/artifacts/<日期>/demo-<时刻>/NN_<状态>.png`。退出码 0 才算 DONE。
实测：`2026-10-24 21:28` 一键跑通，7 张关键帧、12 状态、`late_events=0`、落点误差 25 mm。

### 2.1 手动分步（调试用）

```powershell
Set-Location 'E:\毕设'

# 0) 先只读：确认真没有在跑
& .\.dsh\step3.ps1 -Action Status

# 1) 冷启动（50mm 实验世界 + 显式运动学支撑）
& .\.dsh\step3.ps1 -Action Start -World q2q_warehouse_grasp50 -KinematicCarry

# 2) 一条 START 跑完整链（内部起 5 个节点，结束按进程组回收）
& .\.dsh\step7.ps1

# 3) 收尾
& .\.dsh\step3.ps1 -Action Status
& .\.dsh\step3.ps1 -Action Stop
```

判读：`step7.ps1` 退出码 0 且 episode JSON 里 `final.state=DONE` 才算通过；
`LAUNCHED` 不等于 PASS。落地是否成立**另看独立门禁**，不看状态机自己说 DONE
（10-24 的 195922 就是 DONE 但没落地的反例，被门禁拦下了）。

## 2.1 现场可视化：Gazebo 与 RViz 都能开（附两条踩过的坑）

> 先纠正一个我当天写错的结论：我曾说「Gazebo 和 RViz 都不行」，**那是错的**。
> 真正的原因是两个可修的环境细节，跟项目能不能演示无关。

### Gazebo：默认的 ogre2 渲染器不行，换 Ogre 1.x 就行

症状：GUI 能开窗，但 3D 视口一片空白，日志报
`Ogre2RayQuery.cc: Attempted to set non-finite origin from camera`。

修法：**加 `--render-engine ogre`**。本机是 VirtualBox SVGA3D（`Accelerated: no`，GL 4.1），
ogre2 这条路在这套驱动上起不来，而 Ogre 1.x 正常。已写进
`sim/robot_bringup/launch/bringup.launch.py`（`gui:=true` 时自动带上），无需每次手敲。

### RViz：`XAUTHORITY` 没给，不是插件坏了

症状：`ros2 run rviz2` 报 `no Qt platform plugin could be initialized`。

真因：从 SSH 起 GUI 时只导出了 `DISPLAY`，**没给 X 授权文件**，Qt 连不上 X。
补上 `XAUTHORITY=/home/ros/.Xauthority` 后 RViz 正常起来（`OpenGl version: 4.1`，31 fps，
RobotModel / TF / Grid 都能画）。

### 推荐的演示结构：headless 栈 + 独立 GUI 客户端

单进程 `gui:=true` 会把渲染和物理/控制器挤在一个进程里，实测**冷启动时
`controller_manager` 可能起不来**（spawner 三次超时 → ensure_controllers 放弃 → 整栈被带走）。
演示推荐：

```bash
# 1) 栈走 headless（快、稳，控制器正常就绪）
& .\.dsh\step3.ps1 -Action Start -World q2q_warehouse_grasp50 -KinematicCarry

# 2) 另开一个 GUI 客户端挂到已经在跑的服务器上（渲染崩了也不影响物理与整链）
export DISPLAY=:0 XAUTHORITY=/home/ros/.Xauthority
nohup ign gazebo -g --gui-config ~/.q2q/setup/a200_kinova/gui.config \
      --render-engine ogre > /tmp/gz_gui.log 2>&1 &

# 3)（可选）再叠一个 RViz 看 map / 激光 / 路径
nohup ros2 run rviz2 rviz2 -d /opt/ros/humble/share/clearpath_viz/rviz/nav2.rviz \
      --ros-args -r /tf:=/a200_0000/tf -r /tf_static:=/a200_0000/tf_static &
```

这样渲染失败、关掉窗口、重开窗口都不影响正在跑的任务，答辩时更安全。
实测：这个组合下完整链 **`step7_1024_211150` 一次通过**（DONE、late_events=0、
落点误差 ≈24 mm），底栏显示 RTF ≈100%。

### 备用：自建 2D 俯视图（不依赖 GL）

`.dsh/demo_view_tk.py` 用 Tk Canvas 画实时俯视图（世界轮廓 + `pick_bin` 真值 + 底盘位姿/轨迹 +
状态 HUD）。当窗口系统/渲染出问题时，它是保底手段；答辩投影时它也比分屏 3D 更清楚。

## 4. 这套演示**不**证明什么（写在最前面，防止误读成论文结论）

1. **不是物理抓取**：物体是被 `kinematic_carry` 插件按末端位姿 `set_pose` 带着走，
   不是夹持力，也不是吸附。物理抓取 P7 仍不成立。
2. **不是泛化可靠性**：2/2 通过是**一个固定场景、一种参数**下的结果，不能写成成功率。
3. **不是全故障注入**：正常链是实跑；取消/失联等失败分支是离线事件表（23 条）+
   对两轮 PICKING 记录的 10 s 门槛回放，不是现场注入。
4. **不是连续订单**：投放后没有自动收臂/复位，第二次任务必须先 Stop/Start 回基线。
5. **不是完整 VLM/Harness**：顶层规划、`Subgoal`、Q2Q-VLM、Km-Transformer 仍未实现，
   当前通过的是「中层串行调度 + 低层仿真执行」。

## 5. 演示时最可能踩的三个坑

| 现象 | 真因 | 处置 |
|---|---|---|
| `NAV_TO_PICK` 里 90 s 超时 | 只等到 action 可见，没等 Nav2 生命周期 ACTIVE | 闸门已改为等 ACTIVE；先看 `orch.log` 的「还缺 …」 |
| 抓取段超时/`ROS response exceeded` | 墙钟预算按 RTF≈1 写，仿真变慢后不够 | 用 `--wall-scale` 放大墙钟，**不动物理判据** |
| DONE 但落地门禁失败 | 投放位姿/坐标系错（10-24 是漏了四元数 `w=0`） | 看门禁 JSON 的 `xy`/`z`，再查 `place_plan.py` |
