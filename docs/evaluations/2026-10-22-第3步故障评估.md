## 已确认的问题

### 1. 日志定稿与可执行入口相互矛盾

logs/2026-10-22.md 最后一节明确撤回 ROS_LOCALHOST_ONLY=1 和 UDP-only 配置，并记录删除 ~/fastdds_udp_only.xml。
但 .dsh/nav_simple_bt.sh 仍然 export ROS_LOCALHOST_ONLY=1 和 FASTRTPS_DEFAULT_PROFILES_FILE=/home/ros/fastdds_udp_only.xml；开工清单也仍要求加载 /tmp 下的旧配置。

因此照文档/脚本重跑可能重新引入已经撤回的实验条件。不能把这种失败归结为 Nav2 算法或机器人资产不可用。

### 2. 原始日志显示：动作确认先超时，执行却继续

VM 原始日志：

- ~/.ros/log/bt_navigator_11954_1792634859626.log：时间 1792635459.867793791，`Timed out while waiting for action server to acknowledge goal request for follow_path`。
- ~/.ros/log/controller_server_11946_1792634859291.log：1792635459.550842038，`Received a goal, begin computing control effort.`；1792635798.438697629，`Reached the goal!`。
- 同一 controller 日志共 2107 条 `Control loop missed its desired rate of 20.0000Hz`。
- BT 后续还有 compute_path_to_pose、spin、wait、backup 的确认超时及清代价地图服务超时；behavior_server 后续才出现抢占不支持。

**结论**：不能将末尾的 preemption 错误直接当成最初根因。存在“BT 已认为动作失败，但底层动作仍执行”的证据，必须先处理动作生命周期与通信/调度延迟。

nav2.yaml 目前 bt_loop_duration=10、default_server_timeout=20；这些数的单位为毫秒。VM 安装头文件 /opt/ros/humble/include/nav2_behavior_tree/bt_action_node.hpp 也直接使用 std::chrono::milliseconds；该实现确认超时后会返回 FAILURE。

20 ms 确认预算、10 ms BT 周期与已有调度延迟不匹配，是优先验证的假设。当前默认物理步长 0.02 s，旧实验还使用 0.05 s；仿真时钟粒度也应一并记录。**尚未完成单变量实验，不能宣布“把 timeout 改大就一定修好”。**

官方 Humble 实现：[BtActionNode](https://api.nav2.org/nav2-humble/html/bt__action__node_8hpp_source.html)。

### 3. 验收客户端不能证明它声称的结果

.dsh/nav_goal_client.py 存在以下问题：

- 目标 frame 是 map，距离却直接取 platform/odom.pose 与目标相减；没有 map←odom 变换。只有两个坐标系恰好一致时才近似成立。
- 没有检查目标 yaw 误差，正常到位分支也没有验证到位后的持续停稳。
- speed 初始为 0，未检查 odom 新鲜度；没有收到新数据也可能被判成停稳。
- cancel_goal_async() 的 future 被丢弃；没有验证取消是否被服务器接受、原 action 是否进入 CANCELED 终态。
- 正常任务超时就退出，没有取消仍在执行的任务并确认终止。后续测试可能与前一次残留动作互相影响。

因此日志中的 0.233 m 不能直接证明 map 坐标下合格到位；取消失败确实需要重查，也不能靠目前脚本排除残留任务污染。

### 4. 自动化脚本隐藏失败并把实验状态当依赖

.dsh/nav_simple_bt.sh 对 configure/activate 使用 `|| true`，失败后仍继续发目标；依赖 /tmp/q2q_fast 和 /tmp/nav_goal_client.py，重启后未必存在。清场依赖大范围 pkill/pkill -9，难以保证只终止本次启动的进程。

.dsh/run_remote.ps1 会在远端失败后执行 echo，SSH 最终退出码可能变成 echo 的成功；sync.ps1 的构建通过管道 tail 并靠文本匹配判错，也没有可靠传递 colcon 退出状态。它们会让上层误读运行结果。

### 5. 碰撞轮廓比机器人实际尺寸小

nav2.yaml 的两个 costmap 使用 robot_radius=0.2855 m，即日志所列车体矩形 0.9874×0.5709 m 的内切圆。它没有覆盖车头/车尾；该矩形的外接圆半径约 0.5703 m，机械臂等外伸还需另算。

这是确定的几何建模缺陷，不代表已经证明它引发了本次 abort。后续应按实际碰撞几何选择局部多边形 footprint，并兼顾 NavFn 的圆形近似，不能仅把参数换成多边形就假定全局规划也做了完整姿态碰撞检查。

参考：[Nav2 footprint 指南](https://ros-navigation.github.io/mkdocs.nav2.org/jazzy/configuration_and_development/first_time_robot_setup_guide/footprint/setup_footprint/)。这是通用几何原则；具体参数/插件能力以本机 Humble 为准。

## 需要撤回或降级的旧结论

- “bt_navigator 配置需要 6.5 分钟，因为逐个 dlopen 插件”：日志支持某次 configure→activate 相隔约 394 秒，未提供库加载计时，不能证明时间全部花在 dlopen，更不能把它定为正常基线。
- “base_footprint 必须是 URDF 根，否则 Nav2 用不了”：不成立。重点是导航可见的坐标变换和配置一致；原厂 base_link 根本身不是错误。当前翻转补丁可保留待复现，但其必要性不能由惯例证明，也不能只改其中一处随意回滚。
- “GPU 渲染在这台 VM 永远不可能”：历史证据支持当前配置下渲染故障；不足以证明全部后端、相机路径或宿主配置都不可能。近期可以停止投入该问题，保留 headless/RViz 路线，但应描述为当前运行限制。
- “实时率 0.4 是 VM 天花板”：是特定配置观测值，没有隔离分析就不是硬件极限。

## 几何激光可以保留，但需要标明边界

virtual_lidar.py 可作为无图形渲染的导航输入，ROS2 接口仍有价值。不过当前实现用 odom→lidar 位姿去射线查询 world 的静态 box，隐含 odom=world 的假设；里程计漂移后，两者不再天然一致。它也忽略 box 的高度、link/collision 局部偏移与动态物体，且遇到平行射线时没有检查原点是否位于该 slab 内。

当前 lidar 高约 0.431 m，料箱高 0.3 m，二维实现仍会把这些矮箱当作激光截面障碍。这属于模拟传感器简化，不能作为真实激光/独立定位精度的证据。后续可以明确做二维传感器基线，或用 Gazebo world 真值生成一致的传感器输入；无需为了先通过第 3 步开发完整渲染传感器。

## 建议的恢复顺序与停止条件

1. **固定一个运行入口**：保留原文件用于对照，新建最小入口；明确默认 DDS 环境、固定 world 文件、固定参数、只管理本次启动进程。不要再混用 .dsh 中的历史实验脚本。
2. **通信与控制先过关**：独立验证话题、服务、action 确认/结果/取消往返；再启动机器人，检查控制器、/clock、TF 与消息新鲜度。该关不过，不加 Nav2，也不改行为树。
3. **拆开导航定位与执行**：已有地图可复用；先用一致的真值定位或已验证的 AMCL 二选一，确认 map→base 链。单独验证规划，再验证短距离 FollowPath，之后接最小 BT，避免一开始完整恢复树掩盖最初错误。
4. **修正验收器后再宣布完成**：必须同时记录 action 终态、map 坐标下 xy/yaw 误差、新鲜 odom、持续停稳；取消需确认被接受、终态正确、速度归零；每轮结束清楚确认无遗留动作，再测第二目标。

每个小关先设短的排查预算（建议 20–30 分钟）；到时给出原始证据与卡点，不继续扩散变量。只有恢复一个可重复的最小闭环后，才逐个加回仓库、AMCL、完整模型和恢复动作。不能把较长超时当作通过标准。

若最小机器人仿真仍持续出现不可接受的延迟/渲染限制，应把“运行宿主是否合适”单独决策；重写导航算法不能修复图形驱动或虚拟化瓶颈。
