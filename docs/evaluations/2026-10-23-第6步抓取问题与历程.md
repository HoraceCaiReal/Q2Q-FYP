## 2. 物理约束（都是量出来的，不是推的）

1. **车长决定目标距离**：车头到箱面 ≈ 半个车长。Husky 0.987 m → 箱心恒在 base 前 **0.545 m**；
   Jackal 0.508 m → **约 0.26–0.31 m**。
2. **臂的可用前伸**（`compute_ik` 扫描，64 格 × 3 姿态）：桌面高度（z 0.3–0.75）约 **0.5 m**，
   地面高度（z≈0.15）约 **0.4 m**。零位末端在 z=1.23（Husky）/ 1.057（Jackal）——**臂长不能当前伸用**。
3. **低处接近会被自己的前轮挡死**：`move_group` 日志原文
   `Found a contact between 'front_left_wheel' and 'arm_0_lower_wrist_link'`；抬到 z≥0.50 立刻可规划。
4. **夹爪最大开口 112 mm**（关节 0.0 → 指尖间距 112 mm；关节 0.9 → 25 mm）。
   所以箱体必须 ≤80 mm；0.2 m 的料箱物理上张不开。
5. **指尖比 `arm_0_end_effector_link` 多伸 0.125 m**（沿工具轴 0.112 m）——抓取位姿必须按 TCP 算。

## 3. 历程（按发现顺序）

### 3.1 目标够不着（Husky 时代）
- 车顶住箱子停在 `x≈0.90`，一度被误判成「底盘坏了/物理状态脏」；**实际是保险杠顶住箱面**（倒车立刻生效）。
  → 教训：轮子转、车不动，先倒一下车，比查 SHM/进程便宜得多。
- 规划的 `99999` 里有一部分是**自碰撞**（前轮），不是距离；抬到 z≥0.5 就通。

### 3.2 合成感知的边界
- `virtual_camera` 按 SDF 的 `<pose>` 渲染，**看不见被搬动的物体**；抬升后观测位姿纹丝不动。
  → VERIFY 必须用 `object_pose.py`（Gazebo `/world/.../pose/info`）。
- 相机曾隐含 `base == world` 假设；改订阅真值里程计后随底盘移动正确（底盘退 0.075 m，观测点正好前移 0.075 m）。
- TF 命名空间坑：`TransformListener` 在 `/a200_0000` 下拿不到 `map` 帧 → 干脆改用里程计，少一个订阅面。

### 3.3 宽度估计
- 「像素宽 × Z / fx」在斜看时系统性偏小；改为**掩码反投影 + 沿闭合轴取 3D 跨度**。
- 出现过「宽度从 0.4 掉到 0.25」：查掩码 `bbox u=[0,319] v=[0,338]`、`clip_px=659` → **画幅裁切**，不是算法错。
  修法：内参 `fx=fy=380`、相机俯仰 30°→（近距离时）25°。

### 3.4 夹爪方向判反
- 一度把 0.9 当张开、0.10 当闭合，实际相反；结果「张开着推过去」把箱子**推走 0.29 m**。
- 另有一条硬约束：**最大开口 112 mm**，0.2 m 的箱子根本夹不住 → 目标件改 0.08 m。

### 3.5 MoveIt 侧两个固有坑
- `MoveGroup action` 的取消不可靠（4.65 s 才应答、仍走完）；JTC 层 0.002 s 生效 → 改用自建 executor。
- ACM 漏相邻连杆会导致「起始位姿碰撞」；换平台后还发现
  `left_finger_dist_link ↔ right_finger_dist_link` 自碰撞（**MoveIt 看不到 mimic，左指被动值只能取 0**），
  在 SRDF 禁掉这一对后规划才通。

### 3.6 换平台 Husky → Jackal
- 理由：箱心距离 = 半个车长；Jackal 把 0.545 m 降到 0.26 m，落进可达域并留余量。
- 生成阶段通过，但 `model_patches.py` 报「找不到 base_footprint_joint」——**Jackal 的 raw URDF 根就是 `base_link`，没有 base_footprint**。
- 改造三处：① 新增「无 base_footprint」分支（**新建**根 + fixed joint 到 base_link）；② xacro 包装器 name 改为读实际 robot name；
  ③ link 数阈值 30 → 20（A200=34、j100=28）。
- 结果：`[patches] 校验通过：根=base_footprint link=28 joint=27 多父=无 激光=15.0 Hz`；四控制器全 active。

## 4. 当前未解决

**夹爪闭合无阻力（`stalled: false`，目标位 25 mm 直接到位），箱子不动（z 恒 0.62）。**
已经排除/修正的：夹爪方向（已按实测改成 0.0=开、0.9=闭）、开合轴（实测默认竖直开合，已加 90° 自转改成水平）、
目标尺寸（0.08 m < 112 mm）、进给深度（EE 0.17→0.22 两种都试过）。

剩下最可能的两个方向（**未验证，别当结论**）：
1. 指尖虽然在箱体两侧，但**插入深度不足**（指尖 x≈0.28，箱体 x 范围 0.27–0.35），只夹到前缘几毫米；
2. Gazebo 里指面与 0.2 kg 箱体之间的摩擦/接触参数不足，夹住也带不起来。

## 5. 下一步（按代价从低到高）

1. 在 `object_pose` 之外加**夹爪开口实测**：闭合前后量两指尖间距，确认「真的夹到了 80 mm 的箱子」而不是夹空；
2. 把 EE 再往里推 0.02–0.03 m（用 `--no-exec` 先验证规划可行），再合爪；
3. 若仍夹空，检查 Gazebo 侧指面摩擦系数（`mu1/mu2`）与箱体质量，或临时给夹爪加吸附约束做流程验证——
   但**必须标注为简化抓取**，不能当作摩擦抓取已证实。

## 6. 补记：抓取**成功过一次**（随后又掉回台面）

继「夹爪闭合 `stalled: false`、箱子不动」之后，按第 5 节第 1 条量了闭合前后的指尖间距，
量出来的结论推翻了当时的判断：

| 状态 | 两指尖位置（base） | 间距 |
|---|---|---|
| 张开 0.0 | (0.344, −0.048, 0.605) / (0.345, 0.064, 0.598) | 112 mm |
| 闭合 0.95（夹空时） | (0.327, −0.003, 0.655) / (0.324, 0.017, 0.658) | **20 mm** |
| 闭合 0.95（夹住时） | (0.349, −0.038, 0.591) / (0.350, 0.053, 0.586) | **91 mm** ← 箱子在指间 |

并把末端从 z=0.62 降到 **0.58**（指尖比末端高约 0.04，之前一直夹在箱子顶面而不是腰部），结果：

- 合爪后指尖停在 **91 mm**（自由闭合是 20 mm）→ **箱子确实在两指之间**；
- 抬 +0.05：`pick_bin` z 从 **0.6112 → 0.6481（+37 mm）**，跟随上升 → **抓取成立**；
- 再抬到 0.70（那一步是 92 点的大幅重配置）：箱子**掉回台面**（z 0.6481 → 0.5399），抓取失败。

**所以现状是“能夹住、小步抬升能带走、大步重配置会掉”**，而不是“夹空”。
之后再夹没成功是因为箱子已被推到 `world x=1.3375`（base 约 0.417），而我又用了写死的 `x=0.22`——
指尖只到 0.33，够不到箱前面，自然又是夹空。

### 由此得到的三条操作规则（下一步照此做）

1. **抓取目标必须每次从当前观测现算**，不能写死坐标；箱子每被碰一次就前移几厘米；
2. **抬升只走小步**（≤0.03 m/步），避免规划器给出大幅重配置的路径把箱子甩掉；
3. 若小步抬升稳定，再考虑提高夹持力或改指面摩擦，把“能带走”变成“能搬运”。
## 7. 复现条件（重要）：成功那一次和失败那一次差在「车停在哪」

成功的一次（抓取成立、抬升 37 mm）与之后的失败，几何参数几乎一样，差别在**底盘停止位置**：

| 项 | 成功那次 | 之后失败那次 |
|---|---|---|
| 底盘 odom | **0.9204**（真正顶到工作台） | 0.7615（提前停了，没顶到） |
| 箱心到 base 距离 | 约 0.31 m | 约 0.44 m |
| 末端目标 x | 0.22 | 0.326 |
| 合爪后指尖间距 | **91 mm（夹住）** | 20 mm（夹空） |

结论：**抓取前必须先确认「车真的顶到工作台」**（odom ≈ 0.90），否则箱子离得太远，手臂伸到极限，
夹爪的开合方向与插入深度都会跑偏。这条比任何参数调整都重要。

### 另外两条已确认的操作事实

1. **`pick_stand` 也要移出碰撞场景**：否则末端降到 z=0.58 时会被垫高件挡住，规划直接失败
   （日志：`Unable to sample any valid states for goal tree`，OMPL 空转 146 s）。
2. **`pick_bin` 必须移出碰撞场景**：原因同上，接近阶段末端会判成与目标相撞。

### 仍然未解决

在「车没顶到工作台」的状态下，即使坐标按观测现算（0.326）、夹爪姿态与高度都对，仍然 `stalled: false` 夹空。
下一次要做的第一件事不是调参，而是**开够距离**：先确认 `odom ≥ 0.89`，再开始接近。
## 8. 条件全部满足后的最终结果：**能夹住，抬不走**

按第 7 节的条件重跑（底盘顶到位、目标现算、`pick_bin` 与 `pick_stand` 都移出碰撞场景、夹爪 90° 自转成水平开合）：

| 检查 | 结果 |
|---|---|
| 底盘 odom | **0.9214**（真顶到工作台，与成功那次 0.9204 一致） |
| 观测 | 箱前面 `0.26`，宽度 `0.0799`（误差 0.1 mm） |
| 接近 | `(0.22, 0, 0.58)` 规划执行成功 |
| 张开时指尖间距 | **112 mm** |
| 合爪后指尖间距 | **70 mm**（自由闭合是 20–25 mm）→ **箱子确在两指之间** |
| 合爪对箱体位置的影响 | 几乎不动（1.1993, 0.0046, 0.6212） |
| 四次小步抬升 0.61→0.70 | 箱体 z 始终 **0.617–0.625**，**没有跟随** |

**结论：几何、姿态、开合轴、插入深度、底盘位置都已经对了（指尖停在 70 mm 就是证据），
剩下的问题是「夹得住但带不走」——接触摩擦/夹持力不足，不是位姿问题。**

下一步按代价排序：
1. 提高指面摩擦（URDF 里给 finger 碰撞面加 `mu1/mu2`，或给箱体表面加），这是最直接的；
2. 降低箱体质量（0.2 kg → 0.05 kg）先验证“几何通了就能带走”，把摩擦问题隔离出来；
3. 若只是要跑通流程演示，可临时用 attach/吸附约束，但**必须标注为简化抓取**，
   不能写成摩擦抓取已证实（教程第 12 章对此有明确要求）。

**这一条不要再靠“再试一次”**：四次小步、不同深度都试过，箱体一次没跟；需要改接触参数或质量，属于模型层改动。
## 9. 降质量试验：问题不是质量，是「抓取结果不确定」

把 `pick_bin` 从 0.2 kg 降到 **0.05 kg**（惯量同步按 k³ 缩放）后重跑同一套流程：

| 项 | 结果 |
|---|---|
| 底盘 odom | 0.904（已顶到工作台） |
| 接近 | `(0.19, 0, 0.58)`，成功 |
| 张开时指尖间距 | 111 mm |
| 合爪后指尖间距 | **20 mm**（自由闭合值）→ **这次夹空了** |
| 箱体位置 | 几乎未动（1.217） |
| 抬升 | 无跟随 |

**关键观察：同一套几何，两次结果不同。**
第 8 节那次合爪停在 **70 mm**（夹住），这次停在 **20 mm**（夹空）；两次命令的末端只差 3 cm（0.22 vs 0.19）、
箱体位置只差 1–2 cm。也就是说现在的抓取处在**“几厘米就翻盘”的边缘**，所以结果不可复现。

**这不是“再调一个数”能解决的**，因为失败模式在两种之间来回跳：
- 夹空（20 mm）：指尖没真正进到箱体两侧；
- 夹住但带不走（70 mm + 抬升不跟随）：接触摩擦力不够。

### 让抓取变确定的三件事（下一步按序做）

1. **抓取目标改用 Gazebo 真实位姿**，不用 SDF 相机。相机看不见被推动的箱子，而箱子每被碰一次就前移 1–3 cm，
   这正是“两次差几厘米”的来源。`object_pose.py` 已经能直接读实体位姿，把它接进抓取回路。
2. **插入深度加 2–3 cm**（末端从 0.19 提到 0.22–0.24 后再合爪），保证指尖越过箱体前后面。
3. 以上稳定后再谈摩擦/夹持力；在那之前改摩擦只会掩盖位姿不确定的问题。

**结论**：本条不再继续试。第 6 步的“抓取”当前状态是**几何链路已验证、抓取动作不确定**，
文档第 8、9 节把两次不同结果和原因都留了证据。
## 10. 会话收工总结

**这一天的净产出**：平台从 Husky 换到 Jackal 并跑通（含补丁管线改造）、合成感知链路（像素→base→抓取位姿）建立、
抓取工位与动态料箱就位、抓取执行链打通到「夹住并抬升 37 mm」。

**没解决的**：抓取不可复现。同一套几何，一次指尖停在 70 mm（夹住），一次停在 20 mm（夹空）。
根因已定位到**输入侧**：抓取目标来自 SDF 相机，看不见被推动过的箱子。

**下一次的第一件事**：把抓取目标换成 `object_pose.py` 的真实位姿，再谈深度与摩擦。
不要在没有位置真值的前提下继续调抓取参数——那是把不确定的输入掩盖得更深。

**回退路径**：平台可退 `robot_a200.retired.yaml`；世界只多了三个模型（workbench/pick_stand/pick_bin），删掉即回滚。
